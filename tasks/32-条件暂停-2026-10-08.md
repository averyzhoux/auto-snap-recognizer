## 目标

> 需求原话：「给每个模式再都加个设置项，就是一个 bool 的项，用来设定检测到绿色项后
> 是否自动暂停，也就是自动切换到手动或暂停」
>
> 追问后追加：「那就再加一个设置项，也就是多选，让用户自己设置可以怎么定范围，
> 黄色、蓝色、绿色都可以让人自己选」
>
> 「而且每个模式的这个功能要不相关，功能一致，但是独立设置，就像抓帧间隔那样」

一句话：**连续运行中一旦扫到指定颜色的命中，就自己停下来**。
停法分两种，「暂停」这个词在两类管线上不是同一个东西：

| 管线 | 靠什么停 | 停下来之后 |
|---|---|---|
| 流式 | `analysisPaused = true` | `deliverFrames` 变 false，analyzer 直接丢帧 |
| 其余四条 | `autoMode = false` | 自动抓帧循环停掉，等同切换成手动 |

## 关键设计

### 1. 判据是「显示颜色」，不是 MatchKind

面板上勾的三个色，对应的是结果行**看上去**的颜色：

| 勾选 | 命中条件 |
|---|---|
| 绿 | `isStrong`（Exact / Contains）且未标记 |
| 黄 | 模糊命中，未标记 |
| 蓝 | 该表格项已被手动标记「已识别」 |

★ 这里有个刻意的不一致：一个「**已标记 + 精确命中**」的项，按 `MatchKind` 算它是
`Exact`，但按 [matchColor] 的优先级它显示**蓝色**（人工标记压过自动判定）。
所以只勾绿不勾蓝时，它**不会**触发暂停。

看起来像漏判，其实是照看到的颜色说话——用户勾"绿"的意思是"看到绿的停"，
面板上它是蓝的，就不该停。

### 2. 边沿触发，不是电平触发

只记一个 `lastHitColor`，**只在「上一帧没有命中色 → 这一帧有」时才停一次**。

不这么做的话，停下之后画面里那个绿色还在，用户一点「继续」就立刻又被停住，
等于永远恢复不了。

★ 按用户要求**不做「离开一段时间才算新一次」的宽限**：恢复后命中色仍在画面里
就不再触发，想再停一次得先把它移开（移开后 `lastHitColor` 变回 null，又能触发）。

### 3. `pausedByHit`：区分「程序停的」和「用户按的」

`autoMode = false` 和「暂停」在界面上是同一个样子。没有这个标志的话，
用户**自己**按掉自动模式也会亮起绿色提示环。

```
绿色环的判据 = 暂停中 && pausedByHit
```

它只在三处清零：切管线、离开取景页、用户点那个圆钮。见下面「坑」第 2 条。

## 设置项形态

```kotlin
val autoPauseColors: Map<Pipeline, Set<HitColor>> = emptyMap()
```

字段全局一份，但**值按管线分开存**——和 `captureIntervalMs` 一样：功能相同、
设置互不影响。空集 = 这条管线不开这个功能，**不另设总开关**：默认全不勾。

存储：每条管线一个 key，用 `putStringSet` 存枚举名。

```
auto_pause_colors.Analysis     → {Green, Yellow, Blue}
auto_pause_colors.SmallCapture → {Green}
auto_pause_colors.Standard     → {}          ← 空集也写，表示「明确没开」
```

★ 读回时**过滤认不出来的名字**，不用 `HitColor.valueOf` 硬转：以后删掉某个颜色时，
旧设备上残留的名字会让硬转直接崩在启动路径上。

## 面板 UI（迭代了四轮）

最终形态是**三行**：

```
条件暂停
命中即停，每条模式各自设置
(●) (●) (●)   绿 = 精确   黄 = 模糊   蓝 = 已标记
```

- 第一行标题、第二行说明、第三行才是选项——说明比标题长得多，并排会把色块挤出去
- **未选中的环用各自的颜色**，不是统一白色。三个白圈长得一模一样，
  得看文字才知道哪个是哪个；彩色环本身就是图例
- 选中 = 填色 + 对勾；未选中 = 只要一圈彩色细环，中间空
- 对勾的黑白见 `HitColor.checkMarkColor`

### ★ 色块的触摸区会决定它的视觉位置

圆只有 18dp，靠 `contentAlignment` 坐在触摸区盒子的正中，所以**盒子比圆大多少，
圆的行内重心就被压低多少**。触摸区取 32dp 时圆心比右侧图例文字低约 5dp，
一眼就看得出歪；收到 26dp 后只差约 2dp。

再往下（24dp）视觉更准，但那已经小于舒适点击区了——停在 26dp 是刻意的折中。
**改这个值要连带想清楚对齐。**

## 模式行下方的提示点

选中的模式标签**正下方**多一排小圆点，是这条模式勾了哪几个颜色：

```
        ⌃            ← 上拉箭头
      流式           ← 模式名
     ● ● ●          ← 勾了绿/黄/蓝就点三个
```

- **只显示当前这条管线**的，不是五条各列一份配置。切换模式时点跟着变
- 居中：放在模式项那个已经 `horizontalAlignment = CenterHorizontally` 的 `Column` 里，
  和箭头、文字天然同轴。不勾任何颜色时画布不占宽度，但**槽位高度照留**
- **固定槽位**：和上拉箭头同样处理，五个模式项都留 7dp 高的点槽，只有选中项往里放点。
  不这么做的话选中项会多出一截，五个标签的文字就不在同一水平线上了
- 用 `Canvas` 一次画完而不是摆一排 `Box`：点数是变的（0~3），画的话只要算好间距和
  居中偏移，不用去凑 Row 宽度

## 坑

### 1. 「继续」不能清 `lastHitColor`

用户点圆钮恢复时，**只清 `pausedByHit`，故意不清 `lastHitColor`**：
那一刻命中色多半还在画面里，清掉的话下一帧立刻又被停一次。

等画面真的移开，`lastHitColor` 自己会变成 null，之后才能再次触发。

### 2. 自动暂停时不要清帧缓存

`ModeSwitch` 那边用户手动切自动/手动时会清 `lastSignature` / `lastMatches`，
但**条件暂停这条路径不能清**——自动停的那一刻，结果面板上那行命中正被用户盯着看，
清了会闪一下再重算。

### 3. `luminance()` 是实验性 API

对勾的黑白本来想按色块亮度算，但 `Color.luminance()` 目前挂着
`@ExperimentalGraphicsApi`。为写死的三个颜色引入实验性依赖不划算，
改成显式 `when` 映射。

### 4. 模式行的每一项都必须留点槽

见上。这和箭头槽当初踩的是同一个坑，写第二遍时又差点漏掉。

## 备注

  这是设计上接受的代价，不是 bug——不要把它当缺陷去"修"

### 已知问题：手动模式也会亮绿环（**已确认，暂不修**）

2026-10-09 用户实测发现，明确决定**保持现状**，不要擅自"顺手修掉"。

**现象**：手动模式下按一次快门，如果画面里有勾选的颜色，「手动」圆钮会套上绿环，
而且**一直绿着**（`pausedByHit` 只在点圆钮、切模式、切屏时才清）。
实际上什么都没有被停下来——`autoMode` 本来就是 false。

**原因**：`maybeAutoPause` 在 `finish` 回调里是**无条件调用**的，没有
`continuousCapture` 判断。而同一个函数的 KDoc 却写着「连续运行时才会被调用」——
**注释说了一套，代码做的是另一套**，这是实现时的疏漏。

**要修的话**（两处，都在 `MainActivity.kt` 的 `maybeAutoPause`）：

```kotlin
val maybeAutoPause: (List<LineMatch>) -> Unit = { result ->
    if (!continuousCapture) {
        // 手动模式：没有「停」可言。但把颜色记下来，
        // 免得用户拍完一张有绿的、再切自动模式时被那个遗留的绿立刻停住
        lastHitColor = HitColor.entries.firstOrNull { it in pipelineSettings.autoPauseColors[pipeline].orEmpty() && result.any { m -> hitColorOf(m) == it } }
        return@maybeAutoPause
    }
    ...
```

影响范围：仅手动模式下的视觉误报，不影响已保存的设置，
也不影响自动 / 流式下条件暂停的实际行为。

### ★ `.phone` 里加一行，必须给它 `position: relative`

手机示意图的取景画面是这么画的：

```css
.phone::before { content: ""; position: absolute; inset: 0; background: <渐变>; }
```

它是 `inset: 0` 的**绝对定位**伪元素，绘制在所有**没有定位**的兄弟子元素之上。
`.ph-modes`（模式行）恰好是 `.phone` 里唯一没写 `position: relative` 的子项——
所以那一行**元素在、高度也在，但整行不可见**，被取景画面盖住了。
`ph-row` / `ph-panel` / `ph-bar` / `ph-ver` 都有 `position: relative`，正是这个原因。

**这个 bug 从模式行写进页面起就存在**，一直没人发现（因为"看不见"而不像坏了）。
往 `.phone` 里加新行时，先加 `position: relative`。

> 排查记录：一开始误判成「flex 空间不足被压扁」，加了 `flex: none`、红底、`min-height`
> 全都不显示；又误判成 `aspect-ratio` 卡死；直到 `--dump-dom` 确认 DOM 结构完全正常，
> 才回头看到 `::before` 这一条。**DOM 对但看不见 → 优先怀疑层叠/覆盖，不是布局尺寸。**
