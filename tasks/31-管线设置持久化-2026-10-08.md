## 目标

> 需求原话：「每个模式的上拉菜单的设置都持久化到一个配置文件里面去」
> 「要实现重启app那种的持久化哦」

面板里的分析间隔 / 降采样长边 / 相册保存间隔 / 只存命中，之前只活在
`remember { mutableStateOf(PipelineSettings()) }` 里，杀死进程重进全回默认值。

## 存到哪

**`SharedPreferences`，名字 `pipeline_settings`**，落到：

```
/data/data/dev.averyzhoux.recognizer/shared_prefs/pipeline_settings.xml
```

为什么不跟 `DatasetStore` / `GalleryStore` 一样手写 JSON 放 `filesDir`：

| | 数据集 / 相册 | 管线设置 |
|---|---|---|
| 数据形状 | 列表，每个元素有结构 | 5 个标量 |
| 需要自己处理 | 结构设计、序号分配、损坏回退 | 没有 |

`SharedPreferences` 是系统给标量配置准备的正规容器，不用 `mkdirs`、不用写
「文件解析失败怎么办」的回退分支，也不引新依赖。

### 是整个 App 一份，不按管线分

面板上那 5 个字段本来就是**一条数据类**（`PipelineSettings`），只是不同管线
显示其中几项：

| 管线 | 显示的项 |
|---|---|
| 流式 | 分析间隔 / 相册保存间隔 / 只保存有命中的帧 |
| 降采样 | 抓帧间隔 / 长边像素 |
| 基础 / 省内存 / 小型图 | 抓帧间隔 |

按管线各存一份，就得把现在全局的 `pipelineSettings` 改成 `Map<Pipeline, PipelineSettings>`，
读取点（`MainActivity` 的限速判断与降采样、`CameraPreview`）全要跟着改，收益只是
「换个模式参数也跟着换」——目前没这个需求。**先按全 App 一份做**，将来真要按管线
分，改 Store 的 key 前缀即可，数据类不用动。

## 怎么写的

`PipelineSettingsStore` 两个方法，**每个字段的兜底值直接取数据类里声明的默认值**：

```kotlin
fun load() = PipelineSettings(
    analysisIntervalMs = prefs.getLong(KEY_ANALYSIS_INTERVAL_MS, 0L),
    downscaleLongEdge = prefs.getInt(KEY_DOWNSCALE_LONG_EDGE, Pipeline.DOWNSCALE_LONG_EDGE),
    captureIntervalMs = prefs.getLong(KEY_CAPTURE_INTERVAL_MS, AUTO_CAPTURE_INTERVAL_MS),
    gallerySaveIntervalMs = prefs.getLong(KEY_GALLERY_SAVE_INTERVAL_MS, GALLERY_SAVE_INTERVAL_MS),
    saveHitsOnly = prefs.getBoolean(KEY_SAVE_HITS_ONLY, false)
)
```

`getXxx` 的第二个参数就是默认值，所以**磁盘上没有这个 key 时自动回落**——
以后加字段只在数据类上改一行，这里自动跟上，不需要写版本迁移。

接线（`MainActivity`）：

```kotlin
val settingsStore = remember { PipelineSettingsStore(context.applicationContext) }
var pipelineSettings by remember { mutableStateOf(settingsStore.load()) }
...
onChange = {
    pipelineSettings = it
    settingsStore.save(it)
}
```

改一项落一次盘。`PipelineSettingsSheet` 本身一行没改——它最初写的时候
就把「持久化」留给了外面。

## ★ 两个坑

### 1. `commit()` 而不是 `apply()`

需求是**重启后还在**。`apply()` 是异步落盘，得等进程还正常活着走完那次调度才
写得进去；`commit()` 同步写，写完才返回。

但 `commit()` 写在 Compose 的点击回调里 = 写在 UI 线程上，点一次标签就可能卡一下。
所以放进一个**单线程**队列：

```kotlin
private val io = Executors.newSingleThreadExecutor { r -> Thread(r, "pipeline-settings-io") }
```

为什么不是 `Dispatchers.IO`：那个池是多线程的，连点两下标签两次写盘会并发，
**落盘顺序不保证**，最后留在磁盘上的可能是先点的那次。单线程串行，
既离开 UI 线程，又保证「最后一次点的赢」。

### 2. 可见性

`PipelineSettings` 是 `internal`，新的 Store 类也必须 `internal`——
写成 `class` 会编译报错：

```
e: 'public' function exposes its 'internal' return type 'PipelineSettings'
```

```xml
<?xml version='1.0' encoding='utf-8' standalone='yes' ?>
<map>
    <boolean name="save_hits_only" value="false" />
    <long name="analysis_interval_ms" value="200" />
    <long name="capture_interval_ms" value="1000" />
    <long name="gallery_save_interval_ms" value="3000" />
    <int name="downscale_long_edge" value="2048" />
</map>
```

**5 个 key 全在**，说明 `save()` 是整份覆盖（连没动过的项也写了一份）——
这是刻意的：只写「改过的那一项」就得在内存里记「哪些项是用户改的」，
和「默认值 = 从没改过」这个前提打架，见下面那个坑。

## 备注

- **不要做「等于默认值就删 key」的优化**：面板上的自填框清空 = `0`，
  而 `0` 在 `analysisIntervalMs` 里是「不限速」、在 `captureIntervalMs` 里是
  「用默认的 1 秒」——是**用户显式选择的值**。删 key 会让「显式设成 0」
  和「从没设过」混在一起。这是任务 25 里那两个 0 语义相反的老坑的延伸。
- 版本号同步 `303` / `v0.3.3-Hephaestus`。
