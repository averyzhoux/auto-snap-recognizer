## 目标

> 需求原话：「把包含完全相同的也归为绿色里面。比如目标是 TH，ATHA 也归为绿色。
> 这一步只需要把黄色范围内的判定规则提取一部分到绿色即可。」
>
> 「在显示匹配结果的时候，不要换行，直接一行显示即可。」

## 一、根因：颜色之前是用「分数」判的，不是用「种类」判的

原来：

```kotlin
val isExact: Boolean get() = isHit && similarity >= 0.999f
```

三层命中被压进**同一个浮点** `similarity`：

| 层 | `similarity` | 颜色 |
|---|---|---|
| 1 完全相同 | `1.0` | 🟢 |
| 2 包含 | **`0.9`（一个魔法常量 `CONTAINMENT_SCORE`）** | 🟡 |
| 3 模糊 | 0.71~0.89 | 🟡 |

也就是说，「包含」是黄色**纯粹因为它被赋了 0.9 这个数**。想把包含改判成绿色，
按这个结构就只能去改那个常量——等于让 `similarity` 开始撒谎（明明只是包含，却声称完全相同），
而且以后再也分不出「包含」和「完全相同」。

这是颜色分类和相似度**耦合**在同一个字段上的必然结果。

## 二、真实数据：值不值得改

先数了一遍相册里 200 张照片、621 次命中：

| 类型 | 条数 | 改前 | 改后 |
|---|---|---|---|
| 完全相同 | 508 | 🟢 | 🟢 |
| **包含** | **12** | 🟡 | **🟢** |
| 模糊 | 101 | 🟡 | 🟡 |

12 条包含命中的真身（去重后 6 种），**全是「表格项确实在这行里」**：

```
6TH-6983              -> TH-6983     多认了一个字符
NO: TS-2797           -> TS-2797     带编号前缀
NoTS 2797             -> TS-2797     前缀和内容粘在一起
JS3247AB TA-9706AJ8   -> JS3247AB    一行里两个标签
JS3247AB TA-8706AŅ8   -> JS3247AB
JS3247AB TA-870GAŅB   -> JS3247AB
```

对照真正该保持黄色的模糊命中：`QS-4185 → JS-4185`（Q/J）、
`TA-868O → TA-8680`（O/0）、`VAO-8098 → TAO-8098`（V/T）——都是 **OCR 认错字母**，
和包含完全不是一回事。

结论：要改的不是判定宽严（一层门槛都没动），而是**颜色映射**。

## 三、改法：加命中种类（方案 B）

### `OcrMatcher.kt`

```kotlin
enum class MatchKind { Exact, Contains, Fuzzy, None }

data class LineMatch(
    val rawText: String,
    val entry: Entry?,
    val matchedOn: String?,
    val similarity: Float,
    val kind: MatchKind = MatchKind.None
) {
    val isHit: Boolean get() = entry != null
    val isExact: Boolean get() = kind == MatchKind.Exact
    /** 完全相同 **或** 包含 → 显示成绿色 */
    val isStrong: Boolean get() = kind == MatchKind.Exact || kind == MatchKind.Contains
}
```

三层各自 return 时把 `kind` 标上（判定条件一个字没动）。
`similarity` 从此回归它本来的含义：**真的相似度**，不再兼职做分类。

### `MatchColors.kt`

```kotlin
internal fun matchColor(match: LineMatch): Color? = when {
    !match.isHit -> null
    match.entry?.marked == true -> MatchBlue    // 人工标记优先级最高
    match.isStrong -> MatchGreen                // ← 改这里
    else -> XiaomiYellow
}
```

### 末尾文案也跟着种类走

```kotlin
private fun LineMatch.noteText(): String = when (kind) {
    MatchKind.Contains -> "（包含）"
    MatchKind.Fuzzy -> "（近似 83%）"    // 真编辑距离相似度
    MatchKind.Exact, MatchKind.None -> ""
}
```

包含现在是绿色、和完全相同**长得一模一样**，这句「（包含）」是唯一能看出
「为什么算命中」的线索；同时它也把误导人的「近似 90%」去掉了——
包含根本不是「90% 相似」。

## 四、结果行改成单行

`MatchRow` 原来是 `Column` 两行（识别文字一行、`→ 表格项` 一行）。改成一行：

```kotlin
Row(verticalAlignment = Alignment.CenterVertically, ...) {
    Text(if (match.isHit) "✓" else "·", ...)
    Text(match.rawText, maxLines = 1, overflow = Ellipsis,
         modifier = Modifier.weight(1f, fill = false))
    if (match.isHit) {
        Text("→ ${entry.name}${noteText()}", maxLines = 1, overflow = Ellipsis,
             modifier = Modifier.weight(1f, fill = false))
    }
}
```

两段都给 `weight(1f, fill = false)`：谁短就按需取宽，谁长就在**自己那份**里省略号，
不会出现「一段把另一段挤没」；两段加起来放不下时各自收窄，仍然保持一行。

副作用是同样高度能多看一倍的行数（面板 `heightIn(max = 220.dp)` 没变）。

## 五、旧照片的兼容（容易写错的地方）

相册 JSON 新增 `kind` 字段。**旧照片没有这个字段**，回落规则是：

```kotlin
internal fun parseMatchKind(name: String, hit: Boolean, similarity: Float): MatchKind = when {
    !hit -> MatchKind.None
    else -> MatchKind.entries.firstOrNull { it.name.equals(name, ignoreCase = true) }
        ?: if (similarity >= 0.999f) MatchKind.Exact else MatchKind.Fuzzy
}
```

按**当年的规则**回落，所以旧照片颜色和拍的时候一致：
508 条精确命中仍然是绿的（这条要是写错，几百张旧照片会集体变黄），
12 条包含命中仍然是黄的（刻意不强改——照片记录的是拍摄那一刻的状态）。

抽成**顶层函数**而不是 `GalleryStore` 的私有方法，就是为了能单测：
这条规则写错了**只会静默变色**，不报错、不崩溃，肉眼很难发现。

### 没动的

- **三层判定的宽严一个字没改**（还是那些门槛、那个包含方向限制）
- `MIN_CONTAINMENT_LENGTH = 3` 没动：短于 3 字符的表格项仍然不参与包含判定。
  所以需求里举例的「`ATHA` 包含 `TH`」（2 字符）**仍然是未命中**，不是黄色——
  真放开会让 `TH` 命中任何含 `th` 的行，误命中明显变多
- `CONTAINMENT_SCORE = 0.9` 保留：它还是有用的相似度数值，只是不再决定颜色
