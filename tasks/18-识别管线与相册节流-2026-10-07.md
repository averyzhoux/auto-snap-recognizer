## 目标

> 需求原话：「ABCD以及原来方式都做出来，然后，在类似于小米相机的'选择专业，录像 人像的位置把这些选项放在那里'让使用者自己选择，默认先是原来的方式」
>
> 后续：「流式/自动模式加相册节流，而且进入流失分析后，不再管是否是手动还是自动模式」

三件事，一件是功能、两件是前一件带出来的副作用：

1. 把从相机拿帧、喂给 ML Kit 的方式做成**可选管线**，让使用者按场景自己挑
2. 流式分析不再看手动/自动开关
3. 连续推帧时相册必须节流，否则 200 张上限一分钟左右就写满

---

## 一、五条管线

底色问题：`ImageCapture.takePicture()` 交回来的 `ImageProxy` 要 `toBitmap()` 才能喂 ML Kit，
而全分辨率那张位图是**内存大头**（12MP ≈ 48MB）。不同场景对「省内存」和「认得出小字」的取舍不一样，
所以做成 5 条各自独立的实现，而不是猜一个最优解。

`Pipeline` 枚举（`MainActivity.kt`）：

| 模式 | 取帧方式 | 喂 ML Kit 的东西 | 取舍 |
|------|---------|-----------------|------|
| **标准**（默认） | `ImageCapture` 全分辨率 | `toBitmap()` → `fromBitmap` | 原来那一版行为，最稳、内存最狠 |
| **省内存** | `ImageCapture` 全分辨率 | `fromMediaImage`（零拷贝） | 省掉一份全分辨率拷贝，仍有 `toBitmap()` 做缩略图 |
| **降采样** | `ImageCapture` 全分辨率 | 缩到长边 2048 → `fromBitmap` | 小字变糊的风险，换 ML Kit 更快 |
| **小图直出** | `ImageCapture` + `ResolutionSelector` | `fromMediaImage` | 让 HAL 直接出 1600×1200，从源头省内存 |
| **流式分析** | `ImageAnalysis` | `fromMediaImage` | 相机推帧，不靠定时器 |

UI 上放在**底部模式文字行**（`PipelineModeRow`），位置参照相机 App 的「专业 / 录像 / 人像」那一排；
选中态用小米黄。默认选中「标准」，保持和以前完全一致的行为。

```kotlin
val usesAnalysis: Boolean get() = this == Analysis     // 只有 D 用 ImageAnalysis
val usesBitmap: Boolean get() = this == Standard || this == Downscaled  // 只有这两条需要位图
```

### 非位图管线的位图策略

省内存 / 小图直出 / 流式这三条，`toBitmap()` 出来的位图**只用来做缩略图**，
喂给 ML Kit 的是 `InputImage.fromMediaImage(image.image, rotation)`——零拷贝，不多占一份全分辨率内存。

关键坑：`fromMediaImage` 要的是 `android.media.Image`（从 `ImageProxy.image` 拿），
而且**必须等 ML Kit 回调结束才能 `image.close()`**。所以 `image.close()` 挪进了 `finish` 回调里，
而不是 `finally`。写错就是 native 崩溃。

## 二、流式分析不看手动/自动

原来流式分析的 `ImageAnalysis.Analyzer` 里是：

```kotlin
if (autoMode || manualShotRequested.getAndSet(false)) onFrame(image) else image.close()
```

默认是手动模式，所以进了流式分析还得再去点一下「自动」才有连续识别的效果——很反直觉。

改成无条件处理：

```kotlin
useCase.setAnalyzer(captureExecutor) { image ->
    // 流式分析就是「一直处理」：手动/自动开关对这条管线不生效
    onFrame(image)
}
```

`ImageAnalysis` 本身用 `STRATEGY_KEEP_ONLY_LATEST`，而且**上一帧 `close()` 之后才推下一帧**，
所以语义就是「识别完立刻拿最新的一帧」，天然不需要 `AUTO_CAPTURE_INTERVAL_MS`，
也不会堆积。为此删掉了 `manualShotRequested` 这个 AtomicBoolean。

配套的 UI 改动（不然按钮点了没反应会让人以为坏了）：

| 控件 | 流式分析下 |
|------|-----------|
| 右侧模式开关 | **禁用**，显示「连续」，黄色描边 |
| 快门按钮 | 调暗、不可点（`externallyDriven`） |
| 结果面板「重拍」 | 隐藏 |

引入一个派生状态统一表达「相机在持续推帧」，UI 和节流都用它：

```kotlin
val continuousCapture by remember {
    derivedStateOf { pipeline.usesAnalysis || autoMode }
}
```

> 用 `derivedStateOf` 而不是普通 `val`：`processFrame` 这个 lambda 会被
> `DisposableEffect` 捕获一次并长期持有，普通 `val` 会把**当时的**布尔值冻进去；
> 委托读的是「当前值」，切模式后立刻生效。

## 三、相册节流

### 问题

`processFrame` 原来是**无条件** `saveToGallery` 的——每处理一帧就写一张。
流式分析由相机持续推帧（实测约 **5.5 fps**），按这个速率 200 张上限**半分钟（约 36 秒）**就满，
满了之后开始淘汰旧照片，而且磁盘一直在写（每张约 45KB）。

> 起初以为「静态画面走指纹复用、不跑 ML Kit，能贴着相机帧率出帧」是最坏情况。
> 实测**不是**：手持时 32×32 指纹几乎从不重复（293/294 帧都真的跑了 ML Kit），
> 所以真正起作用的只有 3 秒时间闸门。

### 规则

**不是每一帧都进相册。** 两个 `saveToGallery` 调用点（指纹复用分支、OCR 完成分支）
都套在同一道闸里，没有旁路：

```kotlin
if (shouldSaveToGallery(signature)) { saveToGallery(...) }
```

```kotlin
val shouldSaveToGallery: (Long) -> Boolean = { signature ->
    if (!continuousCapture) true                 // 手动拍摄：每张都存
    else if (signature == lastSavedSignature.get()) false   // 闸①：画面没变
    else {
        val now = System.currentTimeMillis()
        if (now - lastSavedAt.get() < GALLERY_SAVE_INTERVAL_MS) false   // 闸②：太快
        else { lastSavedSignature.set(signature); lastSavedAt.set(now); true }
    }
}
```

`continuousCapture = pipeline.usesAnalysis || autoMode`，流式分析恒为 true，所以闸门对流式永远生效。

两个条件的**参照物都是「上次存盘」，不是「上一帧」**：

| 规则 | 参照物 | 记在哪 |
|------|--------|--------|
| 闸① 画面变了 | 上次**存下来**的那一帧的指纹 | `lastSavedSignature` |
| 闸② 距上次 ≥3 秒 | 上次**存下来**的时刻 | `lastSavedAt` |

两个 `AtomicLong` 而不是普通变量：`processFrame` 会从 `captureExecutor` 线程
（指纹复用分支）和 ML Kit 回调线程（`finish`）两处进来。

### 三个容易误解的点

1. **闸②看的是墙上时间，不是抽帧。** 不是「每 3 帧存 1 帧」。
   帧率变了它也不变：5 fps 和 30 fps 都是每 3 秒一张。帧率越高丢的比例越大。
2. **静止画面只留 1 张。** `lastSavedSignature` 一直等于同一帧，闸① 永远挡。
   盯着一个画面 10 分钟也只多 1 张，不是每 3 秒一张。
3. **被挡下的帧不会「记着回头补」。** 闸门逐帧重新判断，被挡时什么都不记，
   所以不是「3 秒一到就把攒下的补上」。

合起来：**相册是「每 3 秒给当前画面拍一张快照」，不是录像。**

由此推出唯一真会漏内容的场景——短于 3 秒、又变回原样的画面：

```
t=0.0  画面 A → 存了（lastSaved = A）
t=1.0  画面 B → 闸②挡（不足 3 秒）
t=2.0  又回到 A → 闸①挡（== 上次存的 A）
t=3.0  还是 A   → 闸①继续挡……  B 从头到尾没进相册
```

手持扫展台不会「变回一模一样的指纹」，实践中很难触发；但对着标签停 1 秒再挪回原处就会丢。

### 三种场景

| 场景 | 存盘行为 | 200 张上限能撑多久 |
|------|---------|------------------|
| 手动（标准 / 省内存 / 降采样 / 小图直出） | 每按一次快门 → 1 张，**从不节流** | 200 次快门 |
| 自动（同上四条管线） | 每 3 秒最多 1 张，且画面要变 | ≈ 10 分钟 |
| **流式分析**（不论手动 / 自动） | 每 3 秒最多 1 张，且画面要变 | ≈ 10 分钟 |

`GALLERY_SAVE_INTERVAL_MS = 3_000L`。嫌稀就调小，代价是上限时间等比缩短
（1500ms → 约 5 分钟）。

### 每张存了什么、多大

磁盘路径对五条管线**没有任何分支**，都是 `GalleryStore`：

```text
filesDir/gallery/
    000747.jpg     480px 宽 JPEG（质量 85）
    000747.json    { id, time, lines[], matches[] }
```

真机实测（18 张的平均值）：

| 文件 | 平均大小 |
|------|---------|
| `.jpg` | **41.0 KB** |
| `.json` | **3.8 KB** |
| 合计 | **≈ 45 KB/张** |

json 比预想的大，因为每行都记了 `text / entry / matchedOn / sim / hit`，
识别 20 行就有 4~6 KB。200 张上限合计约 **8.8 MB**。

超过 200 张后 `pruneIfNeeded()` 从**最早**的开始删，连续跑满约 10 分钟会静默丢掉开头那批。

## 验证

已经做到的：

- `./gradlew :app:testDebugUnitTest :app:assembleDebug` —— 构建通过，33 个单测全绿
- `adb install -r` 覆盖安装成功

**真机实测（用户手动点开「流式分析」后持续扫了约 1 分钟）**：

```text
pipeline=流式分析 in=1440x1080 ocr=MediaImage rot=90
```

| 指标 | 实测值 |
|------|--------|
| 处理帧数 | **294 帧**（其中 293 帧真的跑了 ML Kit，指纹复用只命中 1 次） |
| 时间跨度 | 103.8 秒，但中间有空档（46 秒 + 5 秒），真正推帧约 **53 秒** |
| 连续段帧率 | 17:29:39→17:30:27，47.6 秒 260 帧 → **5.46 fps** |
| 相册新增 | **18 张**（`000730`–`000747`，连续无缺口） |
| 存盘失败 | **0 次** |

53 秒 ÷ 3 秒 ≈ 17.6 ≈ **18 张**——正好卡在闸门上，说明限制全部来自这道闸，没有别的因素。

顺带量到两个和预估不符的事实：

- **分析流没落到 1920×1080。** `ANALYSIS_SIZE` 请求 1920×1080，
  `FALLBACK_RULE_CLOSEST_LOWER_THEN_HIGHER` 在这台机上给了 **1440×1080**（4:3）。
  每帧要 `toBitmap()` 的位图因此是 6.2MB 而不是 8.3MB。
- **指纹复用基本没生效。** 原以为它能让流式贴着相机帧率出帧、是相册爆炸的主因，
  实测手持时指纹几乎从不重复（293/294），真正干活的是 3 秒时间闸门。

## 已知遗留

- `AUTO_CAPTURE_INTERVAL_MS` 仍然是 1 秒，**没有**改成 10ms——那样在标准管线下每帧
  `toBitmap()` 几十 MB，会 GC 抖动甚至 OOM。要更快就该切「流式分析」。
- 结果面板的**抖动**没处理（流式模式下每秒刷新 5 次以上）。计划：滞回 + 运动检测 + 面板定高。
- ~~**翻内部相册时流式分析不会停。**~~ 已在[任务 22](22-翻相册时暂停流式分析-2026-10-08.md) 修掉。
  自动模式有 `if (screen != Screen.Camera) return@LaunchedEffect` 这道闸，但 `ImageAnalysis`
  是 `bindToLifecycle` 绑在 Activity 上的、不看 `screen`；相册和数据集都是同一 Activity 里的
  Compose 覆盖层、**不触发 onStop**，所以那时相机仍在推帧、仍在识别、仍在往相册里塞。
  修法是给 analyzer 加了 `deliverFrames` 判断（★ 参数必须走 `rememberUpdatedState` 才读得到当前值）。
